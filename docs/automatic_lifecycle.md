# Automatic derived Parent lifecycle — implementation

This implements the accepted restricted derived Registry design. It does not
activate it. No operative automatic policy, genesis identity, credential or server
configuration is included. The protected Registry and historical scientific
packages remain unchanged. Existing manual Owner/R4 verification is preserved.

## Connected path

The existing `upstream_refresh.yml` scheduled `continuous-candidate` job selects
`scripts/automatic_lifecycle.py build` only when `AUTOMATIC_LIFECYCLE_ENABLED`
is exactly `true`. Otherwise the existing Genuine v2/v3 path runs unchanged.
Existing construction/publication activation flags and scheduled authority are
also mandatory. Missing or inconsistent configuration fails before construction.

The build authenticates the existing scheduled context and protected initial
BUILD_CANDIDATE Parent using `genuine_continuous_execution._authority`. A
REGISTRATION_ONLY root cannot start this path. It verifies the derived chain,
clones exact current-Parent/target sources, reuses incremental assembly,
independent Full reconstruction, frozen R2 and unchanged Q1, and seals the run.
A source pair already present in the selected Parent produces NO_UPDATE.

`automatic-parent-writer` is a separate Environment-bound job. Its pre-token
step independently downloads the original successful build Artifact, checks
Artifact-to-Run attribution, ZIP digest and safe extraction, resolves the Parent
again and verifies all native scientific evidence. Rejection prevents the App
private-key action. The read-only build job has no Writer Environment or key.

The Writer repeats these checks after obtaining a verified repository-scoped
installation token. Only an eligible Candidate can be published and appended.
Publication uses the existing GitHub publisher and full-byte downloader: draft,
exactly `candidate.tar.gz`, `notices.zip`, `admission.json`, independent complete
Draft downloads, publication, immutable readback and three complete downloads.
Notices retain seven individually pinned texts and both Parent/target Git tree
license proofs. They provide no blanket legal authorization. Changed license
bytes require a separately reviewed policy; copying assets is not legal approval.
Archive extraction reuses the existing Candidate consumer's pre-read PAX limits,
regular-member/path/count/size checks. Native formats are verified separately.

An uncertain upload/publication stops. The sanitized publication journal records
bounded read-only reconciliation. No retry, replacement, deletion or retagging
is performed. A partial draft or published-but-unintegrated result needs explicit
recovery review. It is never silently converted into a Parent.

## Scientific contract and historical compatibility

`genuine-continuous-candidate-v4` is an explicit native automatic evidence format.
It is needed because Genuine v2/v3 require original research restrictions and
cannot legitimately produce automatic approval. They are not converted or
reinterpreted. The accepting `AUTOMATIC_QUALITY_V2` path is explicitly separate
in P8 and promotion; their existing entry points retain historical behavior.

The protected lifecycle policy pins the exact source policy, frozen build and
benchmark, Q1 implementation, historical R2 rows, implementation contract,
repository, root revision/Registry, generation/commit bounds, license bindings,
Rulesets, App, Environment, deployment configuration and validity interval.
Its raw-byte SHA comes from independent deployment configuration. The policy
is Git-tracked and the checkout must match the actual protected implementation.
No operative policy or invented future commit is generated by this change.

The new original decision requires complete source/material bindings, exact Full
Parity, independently constructed Full results equal to target results, actual
frozen-row validation, every strict Hit5/Hit10 cell passing, no historical or
immediate-Parent new loss, and no unsupported/ambiguous/unresolved/semantic or
applicability-review Q1 requirements. There are no score waivers. This does not
change R2 matching, ranking, denominators, benchmark or Q1 mapping algorithms.
The Q1 report itself remains diagnostic; the separate explicit policy makes the
new admission decision. Historical supplementary Q1 never changes original
Q1_NOT_QUALIFIED, QUALITY_REVIEW_REQUIRED or P8_BLOCKED.

A local calculation is not an authenticated producer or execution authority.
The real Publisher additionally verifies the scheduled workflow, exact revision,
completed build job and original Artifact. No accepting PASS JSON is a CLI input.
The current retained genuine Candidates remain unqualified; no new real quality
acceptance is established by fixture tests or this implementation.

## Derived data and single-use transaction

The fixed ref is `refs/heads/ci-v2-authority-audit/derived-parent-state-v1`.
Every commit contains exactly canonical `registry.json` and `lineage.json`, mode
100644, one parent and one appended entry. The independently pinned genesis
contains only the protected root Registry. Existing entries cannot be edited.
No source/Workflow/policy changes or default-branch writes are exposed.

The lineage binds the preceding commit/Parent, exact new reference and immutable
Release assets, policy, actual producer/Writer run, old/new Registry bytes and
transaction identity. The existing reserve/consume/complete protocol is reused
with config v2 policy bindings, without inventing a human Owner decision.
Consumption is independently read back before the data append. Completion binds
the exact state commit and Registry checksum. Consumers reconstruct and verify
this receipt as well as every generation's complete package and original Run.
An appended state without verified completion cannot become the next Parent.

Concurrent successors rely on GitHub force=false ancestry rejection, with exact
prechecks and independent readback. There is no expected-old REST CAS parameter.
Unknown outcomes remain uncertain and consumed claims stay burned. No automatic
retry or rollback of remote state occurs. Policy expiry, changed governance,
stale protected HEAD, partial evidence or replay blocks construction/deployment.
Normal verified advancements need no per-update PR; the protected root, code,
policies and routing configuration still require human review.

Ruleset A has no bypass; Ruleset B must permit only the dedicated App. Contents
write remains repository-wide. Owner-managed governance cannot prevent an
administrator rolling back between observations; no independent guarantee is
claimed. The consumer re-observes the exact pinned governance before use.

## CI-to-Gradio driver integration

`gradio_deployment_adapter.deploy_selected` is the reusable deployment interface.
It checks the protected checkout/policy, re-verifies the complete selected
immutable lineage/Release, registers exact Corpus bytes once and runs the real
existing D3.6 OS-isolated Gradio/BM25 staging check. No HTTP or LLM is started
by staging. Selection reaches the fresh app before application import.

Only a separately reviewed Python `DeploymentDriver` supplies host operations.
No driver import, shell command or provider is accepted from Workflow inputs or
artifact JSON. Its routing activate/restore operations must be durable atomic
expected-active comparisons, handles must prove ownership, and stop must reject
an active handle. `_replace` preserves the previous instance until verified
switch/readback, restores it on failure, refuses to roll back a competing update,
and never kills a possibly active process after an uncertain rollback. Repeated
identical selected identities are idempotent; transient health receipts do not
change deployment identity. Actual host startup/routing/credentials are external
configuration, not a claimed tested production driver.

Local controlled-driver tests cover successive switches, failure and rollback.
They are not SSH, real server process, Hosted construction or production proof.
No host is contacted by the scheduled Writer; it emits immutable selected-state
receipts. A reviewed host integration calls the deployment interface using its
owned driver and read-only transport after separate server configuration review.

## Remaining operational prerequisites

1. Review/merge the protected implementation PR; independently bind its actual
   deployment revision and new Genuine/lifecycle code digests. Do not silently
   update existing deployment Variables or historical implementation pins.
2. Complete the legitimate initial R4 authority operation, if separately
   authorized. The current official Parent remains REGISTRATION_ONLY.
3. Review exact tracked automatic/source/scheduled policies, historical-row and
   license pins, deployment settings and one pinned data-only genesis. No future
   identity is invented. Provisioning refs/Rulesets/credentials is not performed.
4. Verify Rulesets A/B and installation scope. The existing Writer Environment
   requires per-run human review, so automatic mode explicitly refuses it. A
   separately authorized one-time Environment configuration decision is required
   for unattended mode. The manual Owner gate still demands its original reviewer
   setup; it is never silently weakened or relabelled as automatic authorization.
   GitHub's `branch_policy` protection rule must remain present alongside the
   independently checked exact branch selection; automatic mode rejects additional
   reviewer, timer or other approval rules rather than assuming an empty list.
5. Configure/review the actual host-owned driver, storage/routing and existing app
   environment. Do not connect to xiangyullm during code/local testing.
6. Perform separately authorized genuine Hosted and host acceptance. Offline
   fixture successes do not establish real scientific eligibility or deployment.
